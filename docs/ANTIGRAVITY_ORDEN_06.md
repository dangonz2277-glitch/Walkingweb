# Orden 06 para Antigravity — migrar la misma raíz a Next.js y proteger el sitio

El usuario eligió Vercel Hobby y pidió **protección propia del lado servidor**, sin la función de contraseña de Vercel. El repositorio actual es Vite, no Next.js: ningún `middleware.js` de Next se ejecutaría hoy. Migra **en esta misma raíz WalkingWeb**, conservando la app, los 42 productos, JSON, pruebas y migraciones; no crees una segunda aplicación ni otra carpeta `react-app`. Mantén el último build Vite como referencia hasta comprobar paridad. No toques RLS, pgTAP ni hagas push.

1. Usa una versión estable y soportada de Next.js. En Next 16 la convención se llama `proxy.js` (equivale al middleware solicitado); si se elige Next 15, documenta la convención `middleware.js`. Implementa una página mínima de contraseña y endpoint/acción de login y logout. La contraseña `SITE_PASSWORD` y una clave de firma independiente `SITE_SESSION_SECRET` solo se leen en servidor; `.env.example` contiene nombres y valores de muestra inocuos, nunca un valor real. Fallar de forma cerrada si falta alguna variable.
2. Compara la contraseña suministrada con una operación de tiempo constante sobre digests de longitud fija. La cookie de sesión debe estar firmada, tener expiración comprobada del lado servidor (20 días como máximo inicial), `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` en HTTPS y una política local HTTP que permita probarla sin debilitar producción. Rotar la clave de firma invalida sesiones. Protege contra redirección abierta tras login y evita cachear respuestas privadas o de autenticación.
3. Intercepta `/`, las rutas internas y los endpoints propios que entreguen datos protegidos; exceptúa solo login/verificación/logout y callbacks Auth que realmente existan. El Auth de Supabase externo no necesita una excepción ficticia en la app. Excluye `_next/static`, favicon y recursos estrictamente públicos, pero **no incluyas el catálogo/guía/errores ni secretos dentro del bundle público o HTML público**, porque esos assets quedan accesibles por URL directa. Mueve datos internos a lecturas server-side protegidas o protege sus rutas de assets si esa arquitectura lo requiere. Revisa precarga, RSC/data routes y caché. No confíes en una ocultación de UI.
4. Pruebas HTTP reales en `next dev` y `next start`: sin cookie, `/`, ruta profunda, datos y API propios redirigen/deniegan; login correcto emite cookie y permite acceso; contraseña equivocada, cookie falsificada, expirada y rotación de secreto fallan; logout revoca la cookie del navegador; assets públicos permitidos no exponen el catálogo. Comprueba que el flujo de Supabase Auth de Mi Reporte sigue funcionando y que sus tokens nunca entran en la cookie general. Prueba también origen HTTP local y HTTPS simulado/preview para el atributo `Secure`.
5. Conserva pruebas SQL/API existentes y añade checks de Next/React para paridad del catálogo, guía y reportes. Actualiza CI, scripts, README y plan: la versión con servidor ya no puede abrirse como `file://`; si se conserva un artefacto offline, documenta que es legado separado y no protegido por la contraseña. No despliegues ni publiques hasta la revisión de Codex.

La implementación de la Orden 05 aún requiere los ajustes de `ANTIGRAVITY_REVISION_05.md`. No marques esta orden lista con un middleware suelto en la app Vite.
